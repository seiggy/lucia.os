# OpenBao foundation

<WhoWhatWhy
  who="Developers changing the OpenBao foundation service."
  what="The provisioner's opt-in settings, the identity AppHost resource, image policy and isolated qualification runner."
  why="Secrets storage must not become a startup dependency for the services needed to recover it."

The implementation adds foundation preparation and independent backup tooling. It does not yet add a .NET secrets client, change controller credential stores, or deliver OpenBao references to node agents. [The operator page](../deploy/secrets.mdx) covers deployment boundaries and the recovery gate.

## Ownership

| Source | Responsibility |
|---|---|
| `tools/identity/provision.py` | Validates and stages the explicit private endpoint, creates persistent directories, renders HCL and reports the verified health state |
| `src/Lucia.Homelab.Identity.AppHost/AppHost.cs` | Adds `identity-openbao` when configured and still identity-owned; excludes the independent Spark stack |
| `tools/identity/openbao_stack.py` | Recovers existing storage into its own Compose project, applies owner start/stop requests and reports seal state |
| `src/Lucia.Homelab.Server/Stacks/OpenBaoStack.cs` | Exposes owner-only status/start/stop without accepting container configuration or credentials |
| `deployment/identity/start-openbao.sh` | Waits for the verified leaf marker, starts production server mode and reloads a renewed leaf |
| `deployment/identity/openbao-health.sh` | Accepts reachable sealed or uninitialized instances without labeling them ready for secret operations |
| `deployment/identity/openbao-operator-policy.hcl` | Bounds operator administration to installation-named mounts, auth and policies; denies raw storage and root generation |
| `deployment/identity/openbao-backup-policy.hcl` | Allows snapshot reads and token self-revocation, without secret reads or policy changes |
| `tools/identity/openbao_backup.py` | Captures Raft snapshots, invokes restic, records freshness and explicitly installs the independent systemd user timer |
| `tools/identity/openbao_access.py` | Registers owner-only Authentik OIDC, prepares JWT validation without app roles, and publishes private verified-TLS ingress after scoped operator configuration |
| `src/Lucia.Homelab.Server/Domains/OpenBaoDnsRegistration.cs` | Validates profile-bound OpenBao DNS intent for the existing DNS reconciler and domain operations view |

| `tools/runners/platform_images.py`, `platform_update_worker.py` | Accept existing manifests without OpenBao and refuse automatic OpenBao upgrades |

<Source path="tools/identity/provision.py" /> keeps OpenBao settings separate so existing identity settings retain their repeat-safe equality checks. Both the Python provisioner and AppHost validate the private IPv4 address and endpoint collisions. The AppHost includes the image in the deployed manifest only when the resource is configured; the host never invents an OpenBao row for an old manifest.

The bootstrap and host-deployment payloads ship the shell scripts, policies and access/backup tools with the existing provisioner. Neither path opts an installation into OpenBao, publishes an access route or installs a backup timer.

## Independent stack management

The Spark worker owns the pinned Compose definition and original bind mounts. The controller writes only `{schemaVersion, generation, desired}` to `openbao-stack/request.json`; `desired` accepts `running` or `stopped`. The worker's applied-generation journal lives outside the controller mount. Arbitrary images, deletion requests and unseal values are rejected.

`GET /api/host/openbao-stack` returns status and backup freshness. Owners use `POST /api/host/openbao-stack/start` or `/stop`; the existing owner authorization and CSRF rules apply. The Apps row asks for confirmation before stopping the vault and explains the manual unseal needed afterward.

A sealed response remains sealed in the UI. Missing containers and failed health probes surface as errors; the worker does not restart a sealed vault or silently recreate a missing container after an acknowledged request. A heartbeat older than one minute makes the status unavailable and blocks control requests.

The independent ownership journal is `identity/openbao/stack.json`. The AppHost validates it before excluding the resource. `Provisioner.require_openbao_in_deployment()` refuses a configured identity-owned vault missing from rendered Compose, before deployment can reconcile away its container. An independently owned vault keeps its external identity-network alias without sharing the identity Compose project.

Run the Linux synthetic worker checks with `python3 tools/identity/check_openbao_stack.py`. They cover project isolation, immutable recovery mounts, request bounds and the orphan-deployment guard.

## Native OIDC and private ingress

The access tool reuses `application.py` for registration ownership checks and the active domain's owner group, flows and signing key. It creates a separate `lucia-openbao` application, provider and operator scope mapping. The mapping checks the synchronized group ID through `all_groups()`; user attributes cannot supply an operator claim.

The private `openbao/authentik.json` journal retains installation ownership, issuer and resource IDs. Client secrets stay in a separate `0600` file. Missing secrets, changed origins and unexpected access bindings stop reconciliation. An interrupted binding creation resumes from the journal instead of adding a duplicate grant.

Native browser login uses `lucia-oidc`, with exact callbacks on the chosen HTTPS origin, the `owners` role and an explicit client audience. `bound_claims` requires `lucia_openbao_operator=owner`, even if Authentik's application policy is changed. The role grants only the existing `lucia-operator` policy, with a 900-second TTL and 3600-second hard maximum. Verbose OIDC logging stays disabled.

The separate `lucia-jwt` mount has no roles or default role. Future app integrations must add reviewed identity and path constraints. Its discovery configuration contains no OIDC client secret. External JWTs authenticate at the login endpoint and yield OpenBao tokens; they do not replace OpenBao tokens on secret endpoints.

The configure command accepts the scoped userpass password only through a hidden terminal prompt. It keeps the resulting token in memory and revokes it before route publication, including on configuration failures. Registration and authorization-request generation leave `browser_login_verified=false`; an owner must complete the browser flow.

The generated router joins only `host` and applies a private-source allowlist using the connection address, not `X-Forwarded-For`. The upstream uses HTTPS with `serverName=identity-gateway` and the installed CA copied to `/config/openbao-root-ca.crt`. Both files fit existing gateway mounts, so publication changes no container definition. The separate direct listener remains available for certificate authentication; forwarded certificate headers are never identity proof.

The native tool also writes only `{schemaVersion, profileId, origin}` to the controller's domain-state `openbao-access.json`. `OpenBaoDnsRegistration.Read` requires the active profile and a distinct single-label hostname under its private namespace. It derives the answer from the reviewed gateway address rather than accepting an arbitrary IP from the file.

`ManagedNodeDns` includes that record in its existing desired set, using `ILocalDnsProvider` and the normal ownership journal. The Domains view reports missing, matching or conflicting DNS state. App and external-route validation reserve the registered hostname. Older installations without the intent file add no record. Removing the registration retires only the DNS record Lucia owns; it does not revoke tokens or remove the separate gateway route.

## Startup and renewal

There is no `WaitFor(openbao)` dependency. The CA and its renewer retain their existing startup path. OpenBao waits locally for `certificates/ready.sha256` to match the supplied leaf and key before starting.

The wrapper starts `bao server` against the generated HCL:

```hcl title="openbao/config/server.hcl"
storage "raft" {
  path = "/bao/data"
  node_id = "controller"
}
```

Raft uses controller-local persistent storage and `disable_mlock = true`. The wrapper sets `TMPDIR=/bao/data` so snapshot restoration can stage files without a writable container root. No development server or automatic initialization runs. Certificate renewal sends `SIGHUP` after the published hashes change and validate. The wrapper forwards termination to the server and stops its watcher.

The container's CLI health check verifies the supplied CA with the existing `identity-gateway` certificate name. `bao status` exit codes `0` and `2` both indicate a reachable listener; only `0` means unsealed. The provisioner's public health call reports `ready`, `sealed`, `uninitialized`, `standby`, or `unavailable` without authentication.

## Audit and backup

The generated HCL declares the file audit device with `log_raw=false` and `hmac_accessor=true`. Audit API creation remains disabled. The setup user's configuration owns audit changes; the scoped operator can inspect audit state. A failed enabled destination is a service failure, not a reason to run without auditing.

The backup script reuses the provisioner's endpoint validation and atomic private-file writer. It refuses linked inputs and requires private owner permissions on Linux. Configuration records the explicit retention and independently verified custody; the live seal status must match that share count and threshold.

A dedicated AppRole login issues the snapshot-only policy with a lifetime capped at one hour. The script verifies TLS using the installed CA, refuses redirects and ignores proxy environment settings. The issued token is revoked after download, before slow repository work. Credentials never become command arguments or journal bodies.

For a `127.0.0.1` publication, the job uses the service certificate's `localhost` name instead of the controller's LAN hostname. Other bind addresses retain the existing identity hostname. The offline checks cover both address choices with a distinct controller hostname.

Restic receives the existing repository and password-file path through its environment. Inherited restic and OpenBao credential variables are removed. A real CIFS/NFS mount is required before each restic operation. The script checks the compressed snapshot through EOF before backing it up; truncated downloads fail without pruning or a success record.

Foundation retention uses `lucia:foundation=openbao` with an empty grouping selector. App backups retain `lucia:stack=` tags. Those prefixes keep ownership separate in the existing repository; the foundation job has no dependency on node sync. The private status is unhealthy after 24 hours or any failed/interrupted run. Concurrent runs use a local advisory lock.

`install` creates the setup user's systemd service and daily timer only when explicitly invoked. It requires an existing restic installation and enabled user lingering. Ordinary provisioning only ships the tools. No source path installs a timer, initializes storage or submits unseal shares implicitly.

## Update policy

`manual` lists patch, minor and major offers with `applicable: false`; same-tag rebuilds are also inapplicable. The frontend parser recognizes that policy, excludes its offers from **Update all patches**, and retains the manual-unseal warning for mixed-service requests.

The worker checks the trusted manifest before registry access and refuses the manual policy, including rebuilds. It never invokes its ordinary image rollback path for an OpenBao update. That path cannot undo a Raft format change.

## Checks

Existing check projects cover shared image policy and frontend parsing. The identity check script can publish synthetic Aspire artifacts without starting any service:

```powershell
uv run --no-project python tools\identity\check_openbao.py --render
uv run --no-project python tools\identity\check_openbao_access.py
uv run --no-project python tools\runners\check_platform_images.py
dotnet run --project tests\Lucia.Homelab.DomainChecks
```

The renderer downloads the existing checksum-pinned gateway plugin when its disposable state lacks it. It checks both opt-in and disabled graphs, including the private published port and mounts.

<Source path="tools/security/check_openbao.mjs" /> runs the production HCL and startup scripts in disposable Docker resources. It uses synthetic certificates and Shamir shares; no operational vault or lab endpoint is read.

```powershell
node tools\security\check_openbao.mjs `
  --image openbao/openbao:2.7.2@sha256:5046911075e137e154ce49ab051502f4ec7cf367d484ae4a4dce665d9b90561f `
  --phase foundation
```

The fixture checks verified TLS, rejection of an unrelated CA, repeat initialization refusal, manual unseal, certificate reload and persistence across a sealed restart. It also proves a scoped operator login after initial-root revocation, snapshot-only AppRole access, audit HMAC behavior and failure when an enabled audit output cannot write.

The access unit checks cover repeat/interrupted registration, binding collisions, owner claims, exact redirects and credential drift. They also check private-only routing, verified backend TLS, token revocation before route publication, profile-bound DNS intent and the absence of app grants. Domain checks exercise DNS reconciliation, conflicting records and stale or invalid registration. The disposable foundation fixture exchanges an RSA-signed synthetic JWT through the native plugin, rejects the wrong issuer/audience/subject/claim or expiry and an unrelated signing key, and proves secret APIs reject an external JWT used as an OpenBao token. Its returned OpenBao token can read only the fixture's assigned path.

The recovery check uses a digest-pinned disposable restic image. It proves tag-scoped retention leaves unrelated app snapshots intact, then exercises the production Python backup pipeline against the synthetic OpenBao API and real restic. Only the NAS mount check is replaced for that deliberately local fixture repository; ordinary offline checks prove local directories are refused.

An actual snapshot from that pipeline is restored into separate Raft/audit volumes. The fixture proves wrong-seal rejection, unseal with the original synthetic quorum, the secret and policy, a fresh operator login, and continued rejection of the revoked initial root. It records the isolated restore stage's elapsed time. The stopped-instance check still proves unavailability.

The Docker network, long-running containers and volumes have unique labels; helper containers use automatic removal. The runner removes its own resources and temporary state. No operational snapshot or real share belongs in this fixture.

`--platform linux/arm64` selects the ARM64 image. On an AMD64 engine this needs emulation and is not native controller qualification. Only `--phase foundation` is implemented so far. The planned `client`, `migration`, `delivery`, and `all` phases fail explicitly instead of claiming coverage they do not have.
