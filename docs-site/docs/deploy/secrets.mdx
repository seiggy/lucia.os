# OpenBao foundation

<WhoWhatWhy
  who="Operators preparing a secrets service for Lucia."
  what="The opt-in OpenBao container, its TLS listener and persistent state, and the gates before initialization."
  why="Recovery must still work when the controller is down or the secrets service is sealed."
/>

OpenBao is the selected secrets backend. This integration prepares the foundation service and its recovery tools. **Lucia's credential stores and managed apps still use their existing storage and delivery paths.** No automatic migration runs.

OpenBao uses MPL-2.0, rather than MIT. The integration uses the official `openbao/openbao:2.7.2` image, pinned to a multi-architecture digest in <Source path="src/Lucia.Homelab.Server/Platform/PlatformImages.cs" />.

## Prepare without deploying

The identity provisioner can stage OpenBao before its first deployment. An ordinary desktop install or identity update does not enable it. Once recovered into the independent Spark stack below, OpenBao has its own Compose project and management service.

This example stages configuration on loopback. Replace the bind address with an approved private interface only when clients need network access:

```bash
uv run --no-project python tools/identity/provision.py prepare \
  --host localhost --state ./private-identity-state \
  --openbao-bind-address 127.0.0.1 --openbao-port 8200
```

On an existing installation, use its existing `--state` and host settings. `prepare` writes files; it does not deploy, initialize, or unseal OpenBao. It also prepares the existing identity inputs and fetches the checksum-pinned gateway plugin.

`openbao-settings.json` records the bind address and port separately from the existing identity settings. Only an explicit RFC1918 or loopback IPv4 address is accepted. Wildcard and public binds are refused. The port must be unused by the identity endpoints and boot HTTP service; `443` and `8445` remain reserved. Docker also refuses a port already held by another process during deployment.

Reruns preserve the endpoint and Raft directory. Changing the endpoint requires a reviewed migration. Existing Raft data without its settings record blocks preparation; restore the record instead of creating a replacement installation.

`publish` generates Aspire Compose artifacts without deploying them. Applying those artifacts is a separate operator-approved deployment. Do not initialize a live instance until the recovery gate below is met.

## State and TLS

Paths are relative to the private identity state directory.

| Path | Purpose |
|---|---|
| `openbao-settings.json` | Explicit deployment opt-in and private endpoint |
| `openbao/config/server.hcl` | Production server configuration |
| `openbao/data/` | Durable, controller-local integrated Raft data |
| `openbao/audit/audit.json` | Declarative file audit output with sensitive strings HMAC'd |
| `openbao/config/openbao-operator-policy.hcl` | Installation-scoped administration policy |
| `openbao/config/openbao-backup-policy.hcl` | Snapshot-only job policy |
| `openbao/backup.json`, `backup-status.json` | Private backup configuration and last-run result |
| `certificates/identity.crt`, `identity.key` | Existing step-ca-issued service leaf and its private key |
| `trust/lucia-root-ca.crt` | Public CA trust |

The container runs as the non-root identity UID/GID with all capabilities dropped and a read-only root filesystem. Only its data and audit directories are writable. Restore staging uses `TMPDIR=/bao/data`; it does not need a writable container root. The container receives no CA signing key, bootstrap administrator credentials, or Docker socket. The Lucia web host does not mount OpenBao's Raft data.

The direct API listener preserves client-certificate proof for the later certificate-auth integration. Keep that port outside public routes and restrict network access to the intended clients. The optional UI/JWT route below terminates TLS at Traefik and opens a separate verified TLS connection to OpenBao; it cannot carry client-certificate proof.

OpenBao reuses the existing service TLS leaf. The independent step-ca renewer publishes a complete certificate marker; the OpenBao wrapper checks its hashes before sending `SIGHUP` to reload the leaf. Renewal does not require unseal shares or a container restart. step-ca remains the certificate issuer.

## Persistent Spark stack

<Source path="tools/identity/openbao_stack.py" /> recovers an existing vault into the separate `lucia-openbao` Compose project. It requires the original Raft databases and configuration; it cannot create an empty vault. Before the first start, it takes and checks a private cold copy at `~/.local/share/lucia/openbao-stack/pre-recovery.tar.gz`. The old container must already be absent.

From the installed bootstrap source directory, run as the existing Spark setup user:

```bash
python3 tools/identity/openbao_stack.py install
systemctl --user status lucia-openbao-stack.service
```

The service requires already-approved user lingering. It owns `~/.local/share/lucia/openbao-stack/compose.json`, keeps the original data bind mounts, and uses the pinned `2.7.2` image. The existing container name and the `identity-openbao` network alias preserve the backup job and Traefik route. The identity network is external to this Compose project; no identity containers are recreated.

`identity/openbao/stack.json` records the new ownership. The identity AppHost excludes OpenBao when that record exists, and the provisioner leaves the stack's configuration alone. Without the record, identity deployment refuses a rendered project that omits a configured OpenBao service. But the installed deployment source must contain that guard; an old bootstrap checkout does not gain it from a local edit.

Lucia shows OpenBao on **Apps**, including its seal state and the last successful backup. Owner-only start and stop requests go through the scoped Spark management service. The web host has no Docker socket or unseal shares. Stop preserves the data; starting a stopped vault requires manual unseal. There is no delete control or automatic image upgrade.

After recovery, open the existing private UI and submit the existing unseal quorum. Confirm that it reports initialized before doing anything else. An uninitialized response is a mount failure to investigate, never permission to initialize again.

## Private UI and Authentik sign-in

<Source path="tools/identity/openbao_access.py" /> adds an owner-approved HTTPS origin for both `/ui/` and `/v1/`. It requires an active domain profile, an initialized and unsealed OpenBao instance, and the existing scoped operator login. The gateway must already have a trusted certificate covering the selected hostname.

Choose an unused hostname under the active private namespace. Configuration registers it with Lucia's existing managed DNS reconciler, which uses the saved AdGuard connection to point it at the private gateway. No separate DNS password or manual rewrite is needed. The Domains page shows the record's state; an existing conflicting record remains untouched.

The route joins only Traefik's `host` entrypoint, never its internet-facing `public` entrypoint. A source-IP allowlist accepts RFC1918 IPv4, loopback and IPv6 unique-local addresses; VPN clients must arrive from one of those ranges. Forwarded headers do not expand that allowlist.

From the installed source directory in the native bootstrap administrative context, register a dedicated Authentik application:

```bash
python3 tools/identity/openbao_access.py prepare \
  --state "$STATE" --origin https://openbao.lab.example.test
```

`prepare` stores the ownership journal in `openbao/authentik.json` and a private client secret in `secrets/openbao-oidc-client-secret`. It creates an authorization-code provider and binds its application only to `lucia-owners`. It leaves Lucia's own sign-in registration alone. A rerun preserves the secret and refuses unexpected callbacks or access bindings.

Run configuration in a private interactive terminal:

```bash
python3 tools/identity/openbao_access.py configure \
  --state "$STATE" --origin https://openbao.lab.example.test
```

Enter the existing OpenBao scoped operator password at the hidden prompt. The command creates `lucia-oidc` for browser login and a separate `lucia-jwt` validation mount, then revokes its temporary operator token before publishing `gateway/openbao.yml`. It never initializes, restores or unseals storage.

Traefik verifies the backend certificate against a public CA copy in `gateway/openbao-root-ca.crt`, using the `identity-gateway` certificate name. No certificate verification is skipped, and no browser ForwardAuth sits in front of API clients. The configuration reload needs no container restart.

DNS intent lives in the controller's domain state as `openbao-access.json`, bound to the active profile ID. The existing background reconciler checks it at startup and at most every five minutes. It manages only records it owns and uses the existing AdGuard fleet's settings and synchronization.

For an installation configured before automatic DNS registration was added, register the already-approved origin without entering the OpenBao password again:

```bash
python3 tools/identity/openbao_access.py register-dns \
  --state "$STATE" --origin https://openbao.lab.example.test
```

Open `/ui/`, choose the OIDC method at `lucia-oidc`, and use the `owners` role. Authentik checks membership by the synchronized `lucia-owners` group ID; the OpenBao role also requires the dedicated operator claim and the exact client audience. Successful login grants `lucia-operator` for 15 minutes, with a one-hour hard maximum. It does not issue root tokens.

Use a standalone browser for sign-in. OpenBao's popup callback calls `window.opener.postMessage`; an embedded browser that detaches the popup can fail with `Cannot read properties of null (reading 'postMessage')` after Authentik accepts the login. Firefox is verified for this rollout. Keep the existing OAuth and proxy protections in place.

The CLI can use the registered direct callback:

```bash
bao login -method=oidc -path=lucia-oidc callbackmode=direct role=owners
```

Only the exact UI callback `/ui/vault/auth/lucia-oidc/oidc/callback` and direct callback `/v1/auth/lucia-oidc/oidc/callback` are registered on that origin. The local CLI callback on port `8250` is not allowed.

Membership changes take effect at the next login. Removing a user from the group does not revoke already-issued OpenBao tokens; revoke those tokens separately when access must end immediately. Local userpass recovery and the snapshot job keep their existing independent access.

### App API access

Apps exchange an accepted JWT at `/v1/auth/lucia-jwt/login` for an OpenBao token, then use that token for secret requests. Ordinary secret endpoints do not accept an Authentik OAuth bearer directly.

The prepared JWT mount has **no default role or application roles**, so it grants no app access. Before integrating an app, review its issuer, exact audience and subject, allowed secret paths, and token lifetime. Creating an Authentik service account alone grants nothing. App JWT signing keys are discovered from the configured issuer; only `RS256` is accepted.

Browser sign-in still needs an end-to-end owner check after configuration. A successful registration or generated authorization URL does not prove that the browser completed login.

## Readiness is not unseal

| State | Health response | Meaning |
|---|---|---|
| Uninitialized | `501` | No vault has been initialized |
| Sealed | `503` | Stored data needs the operator's unseal quorum |
| Ready | `200` | This instance can serve authenticated operations |
| Unavailable | No verified response | The listener, trust, or process needs attention |

The container health check verifies the TLS listener and accepts sealed or uninitialized responses. It **does not claim that secrets are available**. Identity provisioning reports OpenBao's state separately in its completion output. Sign-in, LDAP and the CA never wait for manual unseal.

Restarting the OpenBao container or rebooting the Spark seals the vault. There is no auto-unseal service. Restarting only Lucia's controller or the scoped management worker leaves the independent vault running. Existing apps with previously delivered static values may keep running even while the vault is sealed.

## Recovery gate

Deployment and initialization require separate operator approval. Nothing in `prepare`, `publish`, or the backup tool initializes a vault or supplies unseal shares.

Before initialization, record the Shamir share count and threshold privately, with custody locations in separate failure domains. Also record the off-host restic repository and retention. Keep its password, NAS access and the operator's recovery login available without OpenBao or a working Lucia controller. Never put share values or the initial root token in a ticket, command argument, or chat.

Initialize once through a private, unlogged operator channel using the recorded count and threshold. Place the shares with their custodians and privately verify that a quorum can be recovered. After every restart, submit the quorum interactively; the tools never store or submit it. An initialization error is a reason to inspect state, not initialize again.

Losing enough Shamir shares can make sealed data and snapshots irrecoverable. A root token cannot replace the missing quorum. Rekey while a quorum still exists, using OpenBao's [interactive rekey procedure](https://openbao.org/docs/commands/operator/rekey/). If scoped administration is lost, [root generation](https://openbao.org/docs/commands/operator/generate-root/) also needs the existing quorum. Do both through the private recovery channel.

## Audit and the initial root handoff

The generated `server.hcl` declares the `lucia-file` audit device. OpenBao 2.7.2 refuses API-created devices by default. Keep `unsafe_allow_api_audit_creation` disabled; edit the setup-user-owned server configuration for approved audit changes instead.

The device writes to `/bao/audit/audit.json` with `log_raw=false` and `hmac_accessor=true`. Sensitive JSON strings are HMAC'd; numbers and booleans are not. Store secret payloads as strings. Archive audit files through their own protected backup path, monitor free space, and reopen the output with `SIGHUP` after an approved rotation. Add an independent second destination when one is available. If no enabled destination can write, ordinary API operations fail closed; restore the output rather than disabling auditing.

Use the initial root token only to establish scoped operator access. The supplied operator policy can manage `lucia-secrets`, installation-named policies and auth methods, and Raft recovery. It cannot read raw storage or generate root. This is privileged installation administration, not a policy to give a workload.

The examples assume a separately approved installation, a verified `BAO_ADDR`, and `BAO_CACERT` pointing to `trust/lucia-root-ca.crt`. `$STATE` is the canonical private identity state directory. Keep root and operator authentication in separate private channels; no token value belongs in these command arguments.

In the initial root channel, create the operator policy and a human login. `$PRIVATE_OPERATOR_PASSWORD_FILE` is an existing `0600` file, held outside OpenBao:

```bash
bao policy write lucia-operator "$STATE/openbao/config/openbao-operator-policy.hcl"
bao auth enable -path=lucia-operator userpass
bao write auth/lucia-operator/users/operator \
  password=@"$PRIVATE_OPERATOR_PASSWORD_FILE" token_policies=lucia-operator \
  token_ttl=15m token_max_ttl=1h token_explicit_max_ttl=1h
```

In the separate operator channel, log in with the password prompt. Verify the audit device, mount and policy administration using that identity:

```bash
bao login -method=userpass -path=lucia-operator username=operator
bao audit list
bao secrets enable -path=lucia-secrets -version=2 kv
bao policy write lucia-openbao-backup "$STATE/openbao/config/openbao-backup-policy.hcl"
```

The mount command is first-setup only. An existing `lucia-secrets` mount must remain intact; inspect it rather than disabling or recreating it.

Only after the scoped login works, run `bao token revoke -self` in the **initial root channel**. Confirm that token no longer authenticates, clear it from that channel and its temporary storage, and verify a fresh operator login. Later setup uses the operator, never a retained root token.

## Independent restic backups

<Source path="tools/identity/openbao_backup.py" /> captures a consistent Raft API snapshot, validates its compressed stream, and backs up that file with restic. It never copies `openbao/data`, stops OpenBao, or initializes a repository. The systemd user timer runs outside the web host and node/app scheduler.

The job uses the existing restic repository format and `lucia:foundation=openbao` tag. Retention selects only that tag, with `--group-by ""`, so it cannot forget app-tagged snapshots. Sharing a repository still shares its recovery key; tags are an ownership convention, not a cryptographic tenant boundary.

Mount the approved CIFS or NFS share independently of Lucia. The job checks the real mount before every restic operation and refuses an unmounted local directory. Privately recover the existing repository password into `secrets/openbao-restic-password`; do not create a replacement repository after a password or access error. [App backups](./apps.mdx) describes the existing repository and recovery boundary.

Existing app backups mount the NAS and run restic on managed nodes. The controller's OpenBao job needs its own NAS mount and restic installation, even when it uses the same repository. It does not change the node backup schedule. With `127.0.0.1` publication, the job connects to `https://localhost` on the configured port and verifies the service certificate against the installed CA. Other bind addresses use the existing identity hostname. Local backups do not require opening the API to the LAN.

As the scoped operator, configure the separate backup login:

```bash
bao auth enable -path=openbao-backup approle
bao write auth/openbao-backup/role/snapshot \
  token_policies=lucia-openbao-backup token_ttl=15m \
  token_max_ttl=1h token_explicit_max_ttl=1h \
  secret_id_ttl=720h secret_id_num_uses=0
```

Write its login inputs directly to private files, without displaying the values:

```bash
(umask 077; bao read -field=role_id auth/openbao-backup/role/snapshot/role-id \
  > "$STATE/secrets/openbao-backup-role-id")
(umask 077; bao write -field=secret_id -f auth/openbao-backup/role/snapshot/secret-id \
  > "$STATE/secrets/openbao-backup-secret-id")
```

These are bootstrap exceptions, not root or general-purpose tokens. The job exchanges them for a snapshot-only token and revokes it as soon as the download ends, before waiting for restic locks. Rotate the SecretID before its `720h` expiry; revoke the previous accessor after the replacement works. Loss or expiry produces an explicit failed backup.

Create `openbao/backup.json` as the setup user, mode `0600`. The paths and retention below are examples, not a selected destination or accepted custody record. Replace them with privately approved values; set each confirmation to `true` only after that recovery check has passed:

```json title="openbao/backup.json"
{
  "schema_version": 1,
  "mount": "/mnt/backup",
  "repository": "/mnt/backup/lucia",
  "keep_daily": 7,
  "keep_weekly": 4,
  "keep_monthly": 6,
  "share_count": 3,
  "share_threshold": 2,
  "custody_confirmed": false,
  "backup_recovery_confirmed": false
}
```

The recorded share count and threshold must match the unsealed server. Keep custody locations in separate private operator records; this file contains no share values. Keep all backup inputs private and recoverable outside the vault.

Install restic on the controller through the approved package-management path. Run and inspect one backup as the non-root Linux identity setup user before installing its timer:

```bash
python3 tools/identity/openbao_backup.py run --state "$STATE"
python3 tools/identity/openbao_backup.py status --state "$STATE"
python3 tools/identity/openbao_backup.py install --state "$STATE"
systemctl --user status lucia-openbao-backup.timer
```

`install` writes `lucia-openbao-backup.service` and `.timer` under the setup user's systemd directory, scheduled daily at `03:00 UTC` with missed runs caught up. It requires user lingering to be enabled already; it does not change host permissions or install packages. Installing or enabling the timer is an explicit operator action, never part of ordinary provisioning.

`status` returns safe JSON and exit `0` only after a successful run less than 24 hours old. A failed, interrupted or never-run job is unhealthy; so is a future timestamp. Exit `2` means unhealthy. Input or I/O errors return exit `1`. The private status includes the last successful restic snapshot ID; the journal reports failures without upstream response bodies or credentials.

A sealed vault produces a failed backup, not an empty artifact. Unseal it and rerun the job after fixing the reported problem. Take another snapshot after each approved migration cutover.

## Restore before migration

An operational restore drill needs separate approval for its Docker host and private handling. Use a disposable isolated container with fresh local volumes, the pinned image and verified TLS. Never restore into live volumes or use a shared untrusted runner. The synthetic qualification runner is not an interface for real snapshots or shares.

Recover the repository access and password without consulting the current vault. Inspect the selected restic snapshot's `lucia:foundation=openbao` tag, then restore it into a private staging directory:

```bash
export RESTIC_PASSWORD_FILE="$STATE/secrets/openbao-restic-password"
restic snapshots --tag lucia:foundation=openbao --no-lock
restic restore "$SNAPSHOT_ID" --target "$PRIVATE_RESTORE_DIRECTORY" --retry-lock 30m
```

Set `RESTIC_REPOSITORY` privately to the approved mounted repository first. The restored tree contains the original private temporary path ending in `openbao-raft.snap`; use that file, not live Raft data.

Initialize and unseal the **empty disposable instance** through the private operator channel. Ordinary restore refuses a snapshot created under different seal material. On that disposable instance only, `bao operator raft snapshot restore -force "$RESTORED_RAFT_FILE"` imports the snapshot and seals the server. Unseal with the **original snapshot's Shamir quorum**, supplied interactively without arguments, files, CI or chat.

Verify the restored operator login, a known secret and its policy privately. Record elapsed recovery time and the restored snapshot ID without recording the secret. Snapshot recovery also rewinds authorization changes, so reconcile identities and revocations before any recovered service is made reachable.

After the drill, remove the disposable containers and their secret-bearing volumes, restored staging files, and temporary credentials. Privately verify teardown. Migration stays blocked until that operational proof and the custody checks pass.

But a Raft snapshot is only part of recovery. Preserve the external server/audit configuration, public trust, CA material and audit archives through their own backup paths. Keep the Data Protection key ring and bootstrap credentials recoverable outside OpenBao. See [Security model](./security-model.mdx). Do not destroy previous protected credential stores until migration verification and an explicit archive-custody decision are complete.

## Image changes

Once deployed, OpenBao appears in **Platform images** with the `manual` policy. New versions and rebuilds have release-note links, but no automatic update action. The setup-user worker refuses OpenBao update requests before changing any image.

An operator-approved upgrade needs a snapshot and release-specific upgrade checks, followed by manual unseal. Putting an older image back does not restore Raft data. [Platform images](./platform-images.mdx) describes the automatic worker used for the other foundation services.

For disposable local checks and source ownership, see [OpenBao foundation in code](../code/secrets.mdx).
